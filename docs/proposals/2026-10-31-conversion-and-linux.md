# 提案：変換の改善と Linux 対応の道筋（2026-10-31）

> これは提案です。どれもまだ実装していません。公開版（main = `ace280d`、0.6.3）のコードを読んで書きました。手元の未公開の変更（AI による見直し、k-best の区切り違い候補など）とはずれている所があるかもしれません。数字はどれも測った結果ではありません。

## 0. 前提として確認できたこと

- 公開版では、AI と小さな言語モデルに渡す文の候補を `TopConversions`（`src/Core/Japanese/JapaneseComposer.cpp:167`）と `ReadBest`（同 `:1724`）が作っています。並べ方は、**コストではなく各句の順位の合計**です（`ForPicksByRank`）。手元の版もここはあまり変えていないとのこと。
- ひらがなとカタカナの候補のコストは `kTransliterationCost`（int32 の最大値、`JapaneseConverter.cpp:35`）で、実質「無限に高い」扱いです。
- 学習（`JapaneseLearningStore`）は「読み → 書き方」だけを覚えます。文脈も区切り方も覚えず、時間による減衰もありません（`lastUsed` は同点のときの順番と、古い記録を消すのに使うだけ）。
- ライブ変換は、1打ごとには後ろの4句だけを変えます（`kOpenPhrases = 4`）。手が止まると `RebuildLive` が**全体を作り直します**。手元の版では、この作り直しに AI の差し替えも乗ります。
- 評価セット postsja は、SNS の投稿を参考に生成した文で、人が書いた文ではありません。

## 1. 統計変換の改善（AI なしでも効き、AI に渡す下書きも良くなる）

### A1. 候補の文を、順位の合計ではなくコストの順に並べる（最優先）

**問題：** 2位の候補が1位とほぼ同じコストでも、大きく離れていても、同じ「2位」として扱われます。そのため、AI に渡す10文に、本当にありそうな文が入りきらないことがあります。取りこぼしの大半は「正解がリストにはあるのに1位でない」ことなので、ここに直接効きます。

**やり方：**
1. 各句の候補ごとに、その句の1位とのコスト差 `delta = cost - phrase.candidates[0].cost` を出します。
2. 一番コストの低い組み合わせから順に取り出していきます（優先度つきキューで k-best を数え上げる、よくある方法）。始まりは全部1位の組み合わせ (0,0,…,0) です。取り出した組み合わせから、どれか1句だけ次の候補に進めたものをキューに入れます。同じ組み合わせが二度入らないようにします。
3. 1文目は、今と同じく表示中の文のままにします。

**注意：**
- 学習、ユーザー辞書、話題による並べ直しで、表示の順番とコストの順番が一致しないことがあります。その場合は表示の順番を優先し、コストは「その位置より前の候補のコストの最小値」で抑える（コストが順番どおりに増えるようにする）のが安全です。
- **ひらがなの候補に、有限のコストを付ける必要があります。** 今の「無限に高い」コストのままだと、コスト順にした途端、ひらがなの文は二度と AI に届きません。たとえば「その句の1位のコスト＋かな1字あたりの減点」にします。**この減点が「漢字にしすぎ」を直すつまみになります**（A3 と組み合わせる）。

**測るもの：** 同じ N（10文など）で、正解がリストに入る率と、組み込んだ状態の1位の正解率。

### A2. 確定した直前の単語とのつながりを見る

`SearchPath`（`JapaneseConverter.cpp:471`）の文頭（`i == 0`）は、直前の品詞（right id）の接続コストしか見ていません。単語ペアの統計（`PairBonus`）は、確定の境目をまたぐと効きません。

- 直前に確定した最後の語を `Node` として渡し、文頭の語との `PairBonus` を足します。
- ライブ変換で確定扱いになった句の後（`UpdateLive` の `ContextAfter`）も同じです。

### A3. 統計に口語を足す（「漢字にしすぎ」の根っこ）

`japanese-lm` パックは、Leipzig のニュース（2019）と Wikipedia（2021）から作っています。統計の側も書き言葉に寄っているということです。

- 口語寄りで、ライセンスのはっきりしたコーパスから単語ペアの表をもう1つ作ります（出どころは要確認）。
- 直前の文脈のくだけ具合（ひらがなの割合、終助詞、「じゃん」「草」など）から 0〜1 の値を出し、2つの表を混ぜます。
- A1 のひらがなの減点も、この値で強さを変えます。
- 学習のやり直しをせずに、「文体の印」と同じ効果を統計の側で出す方法です。

**先にやること：** 人が書いた口語の評価セット（100〜200文）を作ります。postsja は生成した文なので、そこで見えている「完全一致と表記揺れ許容の約29点の差」が実際の人の文でもあるのかを、まず確かめます。

### A4. 話題による並べ直しを2回やる

話題による並べ直し（`costPerTopic`、`JapaneseConverter.cpp` の `Convert` の終わりのほう）は、「他の句の1位の語」との結びつきを1回見るだけです。記者と汽車のように句どうしがお互いを決める文では、1回では足りません。並べ直した結果の1位でもう1回やります。句の数×候補8個なので、ほとんど遅くなりません。

### A5. 区切り方を学習する

Shift+←→ で句の長さを直した操作は、今は学習されません。読み全体と、直した区切りの位置を記録します。次に同じ読みが来たら、その区切りを `Convert` の `fixedLengths` / `breaks` として渡します。

### A6. 文脈つきの学習と、新しさを重く見る学習

- **文脈つき：** キーを「直前の語＋読み」にした記録を足し、なければ読みだけの記録に戻ります（同じ読みを場面で書き分ける人のため。会う / 合う）。
- **新しさ：** `selections` と `rejections` を、使うたびに少しずつ減らしていく（指数的な減衰）形にします。最近の選択が強く効くので、「最近使った語を優先」がそのまま実現できます。

## 2. AI との結びつけ方の改善

### B1. AI に、TEKITO の順位ではなくコスト差を渡す

`SentenceReranker` の事前分布（`prior_`）は順位ごとの値です。A1 で出したコスト差 `delta` を使って、事前分布を `-delta / τ` にします。τ は finetune で学習する1つの値です。

- TEKITO が迷っている所（差が小さい）では AI に任せ、自信がある所（差が大きい）では TEKITO を残す、という判断を自然にできます。
- 手元の AI の「TEKITO の順位を加味」も、順位の番号を使っているなら同じ形に変えられます（**要確認**）。

### B2. 手が止まったときの見直しに、距離で差をつける

今の `RebuildLive` は全体を作り直すので、確定扱いの句も句読点より前も変わりえます。そこで次のようにします。

1. 句読点（、。）や、キャレットからの距離で「ここより前は自動で変えない」位置を決めます。
2. その位置より前の句は、今の `settledPhrases_` の仕組みで固定し、文脈としてだけ使います（`UpdateLive` が settled の句をそう扱っているのと同じ形）。
3. その位置より後ろだけを作り直し、AI の差し替えも後ろだけに効かせます。
4. 前の部分について、AI や作り直しの結果が今の表示と違ったら、自動では変えず、B3 の印を付けます。

margin は「距離 × 変更の種類」の表で変えます（同音異義語 < 区切りの違い < 言語の違い）。表の値は、1打ずつ再生して決めます（C2）。

### B3. AI と TEKITO の意見が割れた所に印を付ける

AI の1位と TEKITO の1位が違うのに margin に届かなかった句は、「どちらも自信がない」所です。計算はもう済んでいるので、必要なのは表示だけです。`DisplayAttributes.cpp` に属性を1つ足し（たとえば点線の下線）、該当する句にだけ付けます。

### B4. 下書きを確かめる形の高速化（CPU 向けの小さいモデル用）

AI に文を一から書かせる代わりに、TEKITO の1位を下書きとして読ませます。AI が違うと判断した位置から先だけを、辞書で変換し直します。計算がほぼ1回で済み、読みにない文も出にくくなります。

### B5. 学習データに足すもの

- 途中で切った文（ライブ変換で、打ちかけの状態を読むため）。
- Mix の迷った区切り（`ChunkJudge` の `either`）の、もう一方の言語の文を「惜しい不正解」として使った順位学習。

## 3. 評価に足すもの

- **C1. 問題ごとの比較：** 2つの版で、正解から不正解に変わった数と、不正解から正解に変わった数を数えます（McNemar 検定）。AJIMEE は200問なので1問 0.5点、postsja は145件なので1件 0.7点です。数問の差は誤差の範囲に入ります。「正解だったものを不正解にした数」は、margin を決める基準としても使います。
- **C2. 1打ずつの再生：** 打つ速さと、止まる間の長さを決めて再生し、次のものを数えます。最後の正解率、表示済みの部分が変わった回数（ちらつき）、キャレットから2句以上前が変わった回数（遅い変化）、Mix で言語がひっくり返った回数、AI の答えが間に合った割合。
- **C3. N 文中に正解がある率：** A1 の効果を見るため。

## 5. Linux 対応の道筋

### 5.1 今の状態（g++ 13 でエンジンだけをビルドしてみた結果）

`tekito_core` の43ファイルを `g++ -std=c++20` でコンパイルしたところ、29ファイルは通りました。止まった理由は次の5種類です。

| 種類 | 場所 | 直し方 |
|---|---|---|
| `windows.h` を使っている | `MappedFile.cpp`（`CreateFileW` / `MapViewOfFile`）、`SortedTsv.cpp` と `RomajiTable.cpp`（`MultiByteToWideChar`、`RomajiTable.cpp` は Shift_JIS のコードページ 932 も）、`NeuralMath.cpp`（`__cpuid`）、`SentenceReranker.cpp`、`ExternalLexiconProvider.cpp`、`ExternalSlangProvider.cpp` | 小さな `Platform` 層を作る。ファイルの割り当ては `mmap`、UTF-8 の変換は自前の関数、CPU の判定は `__builtin_cpu_supports`。Shift_JIS は `iconv` か変換表 |
| `\` 区切りの `#include` | `UserLexiconProvider.h` の `"Core\LexiconProvider.h"` | `/` にする（Windows でもそのまま動く） |
| MSVC 専用の関数 | `SpecialConversions.cpp` の `swprintf_s`（3か所） | `std::swprintf` か `std::format` |
| 入れ子の構造体の既定値 `= {}` | `ChunkJudge.h:52`（`Thresholds`）、`JapaneseConverter.h:151`（`ModelWeights`） | GCC と Clang は、クラスの中で定義した入れ子の構造体を、そのクラスの中で既定の引数 `{}` に使えない（既知の制限）。構造体をクラスの外に出すか、引数なしの版を別に用意する |
| コンパイラーの設定 | `CMakeLists.txt` の `/W4 /permissive- /EHsc /utf-8` | `if(MSVC)` で分け、GCC と Clang には `-Wall -Wextra` を付ける |

### 5.2 一番の落とし穴：`wchar_t` の大きさ

Windows の `wchar_t` は16ビット（UTF-16）、Linux では32ビット（UTF-32）です。エンジンは `std::wstring` を UTF-16 の前提で使っています。

- `LanguageModel::Continue`（`LanguageModel.cpp:63`）は、各文字を `uint16_t` に切り詰めてからハッシュを取ります。Linux では、基本面の外の文字（絵文字、まれな漢字）でハッシュがデータパックと合わなくなります。**32ビットの文字は UTF-16 の2つの単位に分けてからハッシュを取る**必要があります。
- `KanjiSets.cpp:44`、`SentenceReranker.cpp:228`、`SpecialConversions.cpp:369` のサロゲートペアの処理は、Linux では通らなくなるだけで害はありません。ただし「文字数」の数え方が変わるので、テストで確かめます。
- `-fshort-wchar` で16ビットにする手もありますが、標準ライブラリのワイド文字の関数と合わなくなるので、おすすめしません。

方針：**当面は `std::wstring` のままにし、ハッシュ、データパックの読み込み、文字数を数える所だけを「UTF-16 の単位で数える」関数にまとめます。** 全部を `std::u16string` に置き換えるのは大きすぎるので、後で考えます。

**Linux で失うもの・変わるもの：**
- 候補ウィンドウは fcitx5 / IBus が描くので、グラス風の見た目は使えません。意味の表示は、補助テキスト（aux）や候補の注釈に入れることになります。
- TSF の入力スコープ（パスワード欄、ふりがな欄）にあたるものは、Wayland の text-input の「purpose」と「hints」です。対応はアプリと環境しだいです。
- 「ターミナルでは無効」は、アプリの識別（fcitx5 なら program 名）で同じことができます。

**最初の一歩としては段階0をおすすめします。** 変更が小さく、Windows 版の動きは変わりません。それでいて、Windows がないクラウドのセッションでも評価を回せるようになります。今回のように手元の開発チャットが使えないときにも、クラウドで A1 などを試して数字を出せます。
