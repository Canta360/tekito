# 提案：Mix の改善の方向性と、言語処理学会向けの論文案（2026-10-31）

> 提案です。数字はこのブランチ（`claude/fervent-hopper-subjdt`）を Linux で、0.6.3 のリリースの日本語データを使って測ったものです。手元の未公開の AI（LFM2.5）は入っていません。評価の文はどれも Claude が書いたもので、実際の利用者の入力ではありません。

## 1. 今の位置（測った結果）

### 1.1 打ち方ごとの正解率（Mix、Enter で確定、1位の完全一致）

同じ110文（日英が混ざった文）を3通りの打ち方で測りました。

| 打ち方 | 例 | このブランチの前 | 今 |
|---|---|---|---|
| 区切りごとに Space | `kyouno meeting de release no nitteiwo kimemasu.` | 43.6% | **91.8%** |
| 英単語と次の助詞をつなげる | `kyouno meetingde releaseno nitteiwo kimemasu.` | 3.6% | **67.3%** |
| 句読点までまとめて打つ | `kyounomeetingdereleasenonitteiwokimemasu.` | 32.7% | **75.5%** |

（ほかに、短い Mix のセット `chunk_keys` は 79.3 → 88.0%、短いつなげ打ちのセット `mixed_keys` は 35.3 → 67.6%。日本語モード 66.8%、英語 Auto 82.3% は変わっていません。）

### 1.2 打ち間違い（1文に2か所、3通りの入れ方の平均）

| | Space だけで直る | 各区切りで1回選び直せば直る | 区切りごとに直った打ち間違い | 正しく打った文が変えられた率 |
|---|---|---|---|---|
| Mix（前） | 29.5% | 42.6% | 約54% | 0.8% |
| Mix（今） | **38.7%** | **52.1%** | **約63%** | 0.8% |
| 日本語モード | 35.0% | 70.0% | 約62% | 0.0% |
| 英語 Auto | 49.5% | 86.1% | 約72% | 0.0% |

### 1.3 このブランチで効いたこと（大きい順）

1. **Enter のとき、続いている日本語の区切りをまとめて変換し直す**：区切りの位置は句の切れ目として守る。sake / wo / nomu → 酒を飲む。
2. **どちらにも読める区切りは、英語をカタカナにした文の方が自然なら英語にする**：data → データを更新する の方が自然。前後の区切りの選び直しも一緒に行う。
3. **英単語を中に含む区切り（meetingで）は、Enter で崩さない**。
4. **打ち間違えた英単語は、英語として直す**（chaannel → channel）。ただし、英語の直後か、ローマ字ではまず使わない文字があるときだけ。
5. **Mix の日本語の区切りでも、打ち間違いを見つけるモデルを使う**。区切り用に、直すかどうかの基準を緩める。
6. **候補の2番目は、もう一方の言語に渡す**（打ち間違いの候補は後ろ）。

## 2. 残っている誤りと、次にやること

### 2.1 つなげて打つ入力（一番伸びしろがある）

区切って打つ場合の 91.8% と、つなげて打つ場合の 67〜75% の差がそのまま伸びしろです。残っている誤りは次のとおりです。

| 種類 | 例 | 直し方の案 |
|---|---|---|
| `shi` で始まる日本語の前の英語が切り出せない | deployshitekudasai、crashshimashita | 英語を切り出すときに、日本語側を `shi`、`si` のどちらでも読めるようにする。今は英語の末尾と日本語の先頭の境目の候補を絞りすぎている可能性がある |
| 文全体が英語と判定される | Konobranchwomainnimerge… | 句読点までまとめて打った入力では、英語として読む前に「英単語を切り出した日本語」として読んでみる。今の切り出し（最大3語）を句ごとに繰り返す |
| 短い英単語が日本語に負ける | casewo → 枷を、betanano → ベタ、pagewa → パゲ | 区切って打ったときと同じく、Enter で「カタカナにした文」と比べる（ケースを書きます > 枷を書きます） |
| 名前のデータの書き方が強すぎる | timeout → Time Out、code → No Code、bug → BUG | 名前のデータ（Wikipedia 由来）にある複数語・全部大文字の書き方は、文の中の一般の単語には使わない |

### 2.2 打ち間違い

- **短い区切りの打ち間違い**（ktouno → 骨の。モデルの差は 10.2）：区切り単独では手がかりが足りません。**前に確定した日本語の区切りのかなを頭に付けて**モデルに読ませ、差を測ります（直すのは今の区切りの中だけ）。
- **英単語の打ち間違いで、英語 Auto も直せないもの**（deplo、dealine）：日本語の文の中では、英語としての直し方を Japanese text で見かける率だけで判断しています。区切りの外の文脈（前後が英語の名詞を取りやすい「の」「を」か）を判断に加えます。
- **日本語モード**：Space だけで 35% に対し、1回選び直せば 70%。正解は候補に入っているのに1番目に来ていません。打ち間違いの候補の位置と、直すかどうかの基準を、区切りの長さで変えるのが効きそうです（Mix で 12 → 8 に下げたのと同じ考え方）。
- **英語 Auto**：Space だけで 49.5%、1回選び直せば 86.1%、正しい語を変えた率 0%。とても保守的です。自信の基準を少し下げたときに、正しい語を変える率がどう動くかを曲線で測ります。

### 2.3 評価とデータ

- **人が書いた Mix の文**：今のセットはすべて Claude が書いたものです。実際の利用者の書き方（社内チャット、開発のやりとり）とは偏りがあるはずです。100〜200文でも、人が書いたセットで同じ数字を出したいです。
- **1打ずつの再生**（ライブ変換）：前の提案書（`2026-10-31-conversion-and-linux.md`）のとおり、ちらつきと遅い変化を測ります。
- **区切って打つ / つなげて打つ / 打ち間違いの3つを、いつも並べて報告する**（この文書の 1.1 と 1.2 の形）。

### 2.4 AI（手元の LFM2.5）との組み合わせ

- このブランチの「Enter で文全体を見直す」は、文チェックの小さな LSTM でやっています。ここを手元の AI に替えると、カタカナで読み替える工夫なしに英語のまま読めるはずです（AI は英語の入った Mix の文で学習済み）。
- 候補の文をコスト順に並べる直し（A1）は、AI に渡す10文にもそのまま効くはずです。

## 4. 論文案（言語処理学会 年次大会向け、4ページ程度）

### 題名の案

「日英混在ローマ字入力のための区切り単位の言語判定と確定時の文単位再判定」

### 主張したいこと

1. **問題設定とベンチマーク**：日本語の文に英単語を混ぜて書くときの入力（Mix）を、「区切って打つ」「英単語と助詞をつなげて打つ」「句読点までまとめて打つ」の3つの打ち方と、打ち間違いの有無で評価できるデータセットと指標。指標は、1位の正解率、区切りごとの候補の順位（Space の回数）、正しく打った文が変えられた率。
2. **方法**：打っている間は、統計変換と区切りごとの言語判定で、すぐに出す（入力を待たせない）。Enter のときだけ、文全体を見直す。
   - 続いている日本語の区切りを、区切りの位置を守ったままもう一度まとめて変換する
   - どちらにも読める区切りは、英語をカタカナに読み替えた文と比べて、言語モデルで決める（日本語向けの小さな言語モデルでも英語を扱える工夫）
   - 打ち間違えた英単語と日本語の打ち間違いの直し方の順番の決まり
3. **結果**：1.1 と 1.2 の表。特に、つなげて打つ入力で 3.6% → 67.3%、文全体の見直しで 43.6% → 91.8%。

### 論文までに足りないもの

- **人が書いた評価の文**：今の文は Claude が書いたものです。論文では、評価データの出どころと偏りを正直に書く必要があります。人が書いたセットでも同じ傾向が出るかを確かめることが、一番の前提条件です。
- **比較の相手**：Microsoft IME、Google 日本語入力、Mozc、Zenzai（azooKey）が、同じキー列でどうなるか。「Mix のような打ち方は普通の IME では想定外」という点は、それ自体が主張になります。
- **それぞれの工夫を外したときの比較（アブレーション）**：工夫を1つずつ外したときの数字。このブランチのコミットごとに測ってあるので、まとめれば出せます。
- **統計的な検定**：文ごとに、良くなった数と悪くなった数を比べる（McNemar）。
- **速さ**：Enter のときの見直しにかかる時間（Linux で測れる）。
