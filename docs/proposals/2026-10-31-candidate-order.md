# 提案：候補リストの並べ方を1か所で決める（2026-10-31）

> 提案です。1〜2の測り方と、4の最初の2つの直しはこのブランチで実装済みです。それ以外は案です。

## 1. 今どうなっているか

`JapaneseComposer` の候補リストは、候補を**作る場所がそのまま並べる場所を決めて**います。リストの先頭や2番目に差し込んでいる場所だけで、`JapaneseComposer.cpp` に15か所ほどあります。

| 差し込む位置 | 何を | どこで |
|---|---|---|
| 1番目 | 英語（つなげて打った英単語） | `BuildPhrasesFor`（`splitter_->Judge` の後） |
| 1番目 | ひらがな（`KanaCandidates`）、数の書き方 | `KanaCandidates`、`StyleKanaNumbers` |
| 1番目か2番目 | つなげて打った英語の文全体 | `RunTogetherEnglish` の後 |
| 2番目 | もう一方の言語（Mix の `either`） | `BuildPhrasesFor` の終わり |
| 2番目 | 外来語の英語（ミーティング → meeting） | `AddLoanwords` |
| 2番目 | 全角・半角の別の幅 | `AddOtherWidth` |
| 2番目か5番目（`kSlipPosition`） | 打ち間違いを直した読み | `AddSlipCandidatesFor`（**リストを開いたときに**後から入る） |
| 3番目（`kDigitsPosition`） | 数字 | 数字の候補 |
| 途中 | 記号、絵文字 | `AddSpecial` |
| 最後 | 打った形（ひらがな、カタカナ、半角、英字） | `AddTypedForms` |
| 全体を並べ替え | 学習した書き方 | `JapaneseLearningStore::Reorder` |

それぞれは筋が通っていても、**全体としてどう並ぶかを決めている場所がありません。** 後から差し込んだものが、先にいたものを押し出します。

### 測って見つかった例（`eval/ja/chunk_keys.tsv`）

- **2番目の取り合い：** `data` は日本語と判定され、英語は2番目に入ります。ところが、リストを開いたときに打ち間違いの候補（だった）が同じ2番目に割り込み、英語は3番目になっていました（立た、だった、Data）。→ 直しました（4.1）。
- **英語の区切りに、ローマ字の打ち間違い：** online → Online、鬼ね、online、オンライン。英語と判定した区切りなのに、日本語の打ち間違いの候補が2番目に来ていました。→ 直しました（4.2）。
- **意味のない日本語が上のほうに来る：** api → API、api、アプリケーション…、アピ、あぴ、亜日、あ日。英語の区切りの日本語は1つあれば十分で、自信のない漢字の組み合わせを何個も並べる理由はありません。（未対応）
- **文頭の大文字：** 日本語の文の先頭に来た英単語は大文字になります（Data、Game）。評価セットの正解は小文字です。（決めてもらう必要あり）

## 2. 測り方

- 日本語：`tekito_ja_eval --keys-corpus` の `in_list`（正解が最初の9個にある）と、`sentences topN`。
- Mix：`tekito_ja_eval --chunks`（`--hold` なし）が、区切りごとに「その区切りで文が必要とする候補が何番目にあるか」を出します。
  - `chunk_rank1/2/3`：1番目・2番目・3番目にあった区切りの数
  - `missing`：最初の9個に入っていなかった区切りの数
  - `picks`：正解にするのに Space を押す回数の合計
  - `in_lists`：どの区切りも最初の9個から直せる文の割合
- `TEKITO_EVAL_DUMP_LISTS=1` で、区切りごとのリストをそのまま表示します。

並び順を変えるときは、`top1` を変えずに `picks` と `missing` を減らすことが目標になります。

## 3. 提案：「場所の決まり」を1つの関数にまとめる

候補を作る関数は、**どこに入れるかを決めず**、候補に「役割」と「強さ」を付けて返すだけにします。並べるのは最後の1つの関数（たとえば `ArrangeCandidates`）です。

### 3.1 候補に付けるもの

- **役割（slot）：** 次のどれか。
  1. **システムの選択**（今の1番目。文全体の判定と文チェックが決めたもの。並べる関数は変えない）
  2. **別の解釈**（もう一方の言語、打ち間違いを直した読み、つなげて打った英語、区切りの違う読み）
  3. **同じ解釈の別の書き方**（同じ読みの別の漢字、外来語の英語、数字の書き方、別の幅）
  4. **おまけ**（絵文字、記号、顔文字、日付）
  5. **打った形**（ひらがな、カタカナ、半角、英字）
- **強さ：** 比べられる1つの数（変換のコスト差、判定の自信、文チェックのスコアなど。最初は今あるコストを使えば足ります）。

### 3.2 並べる決まり（案）

1. 1番目はシステムの選択のまま。
2. 2番目は「別の解釈」の中で一番強いもの。**別の解釈どうしは強さで比べ**、早く差し込まれた方が勝つ、ということはなくします。Mix で迷った区切り（`either`）では、もう一方の言語が基本的にここに来ます。
3. その後に、同じ解釈の別の書き方を強さの順に並べます。学習した書き方は、この中で前に出します。
4. 1ページ目（9個）には、おまけを**種類ごとに1つまで**入れます（今の「絵文字を1つ」と同じ考え方）。
5. 残りの別の解釈と、別の書き方は2ページ目以降に回します。
6. 打った形はいつも最後です（今と同じ）。
7. 同じ文字列は1つにまとめ、強い方の役割を残します。
8. **自信の低い組み合わせは1ページ目に入れません。** たとえば英語と判定した区切りの日本語は、ちゃんとした単語になる読み（`IsWord`）か、コストが一定以下のものだけを出します。

### 3.3 Mix の「英語も日本語もありうる」単語

ChunkJudge は今、「英語か日本語か」と `either`（どちらもありうる）の印だけを返します。これを、**英語らしさの強さ**（頻度、日本語の文でラテン文字のまま書かれる率、日本語として読んだときのコスト）も返すように広げます。

- 強さの差が大きい：1番目に決めて、もう一方は「別の解釈」として後ろへ。
- 差が小さい（今の `either`）：1番目は文脈で決め、もう一方は**必ず2番目**。
- 文全体を Enter まで保つとき（`--hold`）は、迷った区切りだけ両方の言語で文を作り、文チェックに選ばせます。

## 4. 進め方

小さく分けて、1つずつ `picks`、`missing`、`top1`、`in_list` で確かめます。

1. **済：** もう一方の言語の候補に `otherLanguage` の印を付け、打ち間違いの候補はその後ろに入れる。chunk_keys で picks 33 → 28（chunk-both は 10 → 6）。日本語の打ち間違いのセットは変わらず。
2. **済：** 英語と判定した区切りでは、打ち間違いの候補を2番目に出さない（online → Online、online、オンライン）。
3. 英語と判定した区切りの日本語は、ちゃんとした単語になるもの、または最良の1つだけを1ページ目に出す（3.2 の8）。
4. 候補に役割を付ける（PhraseCandidate に `slot` を足す）。並べ方はまだ変えず、各関数で付けるだけ。
5. `ArrangeCandidates` を作り、差し込みを1つずつそこへ移す。移すたびにテストと評価で確かめる。
6. ChunkJudge が強さを返すようにし、3.3 を入れる。
7. Mix の評価セットを人が書いた文で増やす（今は92文。迷う区切りは12文しかない）。
